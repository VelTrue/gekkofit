# Трекер тренировок — дизайн MVP

Дата: 2026-09-04
Статус: согласовано с пользователем через superpowers:brainstorming, готово к написанию implementation-плана.

## 1. Идея и цель

PWA-трекер тренировок для зала. Пользователь записывает подходы (сеты), повторения и вес по упражнениям во время тренировки, видит историю и прогресс. Приоритет — предельная простота ввода (часто одной рукой, между подходами, в условиях зала) и современный, не «шаблонный» визуальный стиль.

Источники, на основе которых принимались решения дизайна — [research.md](../../../research.md) (параллельное исследование простоты UX, онбординга, визуального дизайна и стека разработки на реальных примерах: Strong, Hevy, FitNotes, Copilot Money, open-source репозитории на GitHub).

## 2. Скоуп MVP

**Входит в MVP:**
- Логирование тренировки: старт тренировки → выбор упражнения → запись подходов (вес, повторы) → завершение тренировки.
- Прогресс представлен как **система мастерства** (см. раздел 5), а не только графиками.
- История тренировок (список + календарь).
- Каталог из 337 предустановленных упражнений (раздел 6), выбор только из каталога.
- Переключатель языка интерфейса RU/EN.
- Полностью рабочий офлайн-режим — приложение целиком локальное, сервера нет.
- Экспорт/импорт данных (резервная копия, перенос на новое устройство) — см. раздел 8.
- PWA: установка на главный экран, работа как приложение; в перспективе — упаковка в APK (см. раздел 9).

**Осознанно вне MVP (не строим сейчас):**
- Аккаунты/авторизация, облачная синхронизация, любой бэкенд/сервер — решили пойти по пути локальных приложений (как GymKeeper, FitNotes): все данные только на устройстве, перенос между устройствами — через экспорт/импорт файла, а не через сервер. Это же снимает вопрос о размещении персональных данных на сервере в РФ — сервера, который бы их хранил, просто не существует.
- Добавление пользователем своих произвольных упражнений сверх каталога.
- Отдельный трекинг веса тела.
- Бейджи/экран личных рекордов (PR) отдельно от системы мастерства.
- Шаблоны/программы тренировок.
- Переключение единиц веса (кг/фунты) — только кг.

## 3. Архитектура

```
┌─────────────────────────────────────────┐
│           React PWA (браузер)             │
│  ┌─────────────┐  ┌────────────────────┐ │
│  │  UI-слой     │  │  Service Worker     │ │
│  │  (компоненты,│  │  (кэш статики,      │ │
│  │  экраны)     │  │  установка PWA)     │ │
│  └──────┬───────┘  └────────────────────┘ │
│         │                                  │
│  ┌──────▼───────────────────────────────┐ │
│  │  Data layer (единственная точка       │ │
│  │  доступа к данным для UI)             │ │
│  └──────┬───────────────────┬────────────┘ │
│         │                   │              │
│  ┌──────▼──────┐    ┌───────▼──────────┐  │
│  │  Dexie/      │    │  Export/Import    │  │
│  │  IndexedDB   │    │  модуль           │  │
│  │  (единственное│   │  (backup-файл)    │  │
│  │  хранилище)  │    │                   │  │
│  └──────────────┘    └───────────────────┘  │
└───────────────────────────────────────────┘
```

Сервера и бэкенда в приложении нет вообще — это осознанное решение (по образцу GymKeeper/FitNotes): все данные живут только в IndexedDB на устройстве пользователя. Перенос данных между устройствами и резервное копирование — через файл экспорта/импорта, а не через сеть (раздел 8).

**Принцип:** UI никогда не работает с данными напрямую — всегда через data layer поверх Dexie. Это по-прежнему полезная изоляция даже без бэкенда: если когда-нибудь в будущем всё же понадобится сервер/аккаунты, менять придётся только data layer и добавить sync-модуль — экраны и остальную логику трогать не придётся.

**Компоненты:**
- **UI-слой** — React + Tailwind CSS, экраны и компоненты.
- **Data layer** — тонкий слой функций (`createSet`, `getExerciseHistory`, `getMasteryProgress` и т.п.) — единственная точка входа для UI к данным.
- **Dexie/IndexedDB** — локальная БД в браузере, единственное хранилище данных.
- **Export/Import модуль** — сериализация всей локальной БД в файл и восстановление из него (раздел 8).
- **Анимации** — библиотека **Motion** (React) для GUI-переходов и анимации повышения уровня мастерства; изолирована в UI-слое, не затрагивает данные при будущих визуальных переделках.

**Хостинг:** для личного использования (первые недели) — можно вообще не деплоить публично, а открывать локальную сборку (`vite build` + `vite preview`, либо dev-сервер) с телефона через локальную Wi-Fi сеть. Публичный деплой статики (когда/если понадобится) — на Vercel или любом хостинге: приложение не хранит и не передаёт персональные данные на сервер, это просто раздача статичных файлов, поэтому вопрос размещения на территории РФ здесь не встаёт — обрабатывать нечего, сервер не видит данных пользователя.

## 4. Модель данных

**`exercises`** — статичный каталог (раздел 6), общий для всех, не привязан к устройству.
`id, slug, name_ru, name_en, muscle_group, sub_group, equipment`

**`workouts`** — одна тренировочная сессия.
`id, started_at, finished_at`

**`sets`** — один подход внутри тренировки.
`id, workout_id, exercise_id, weight, reps, set_order`

**`exercise_progress`** — кэш накопленного прогресса мастерства по упражнению (чтобы не пересчитывать все подходы при каждом открытии экрана).
`exercise_id, total_sets, total_xp, best_weight_ever` (ключ — `exercise_id`)

Без бэкенда и синхронизации схема заметно проще, чем в первой версии дизайна: не нужны `device_id` (данные и так только на этом устройстве), `updated_at`/`deleted_at` (были нужны для разрешения конфликтов синхронизации и tombstone-удалений — без сети это не требуется, удаление просто удаляет запись).

**Уровень мастерства нигде не хранится** — всегда вычисляется на лету чистой функцией из `total_sets` и `total_xp` (раздел 5). Если пороги уровней поменяются позже, миграция БД не нужна.

## 5. Система мастерства (геймификация прогресса)

У каждого упражнения — **две независимые шкалы**, обе растут от накопленных подходов, но по-разному:

**Шкала «Объём»** — считается по `total_sets`: просто количество выполненных подходов этого упражнения за всё время.

**Шкала «Сила»** — считается по `total_xp`, накопленному так:

```
XP(подход) = БАЗА × коэф_веса × коэф_повторов

коэф_веса    = min(вес_в_подходе / best_weight_ever_на_момент_подхода, 1)
коэф_повторов = min(повторы_в_подходе / 5, 1)
БАЗА = 10
```

- `коэф_веса` сравнивает подход с личным лучшим весом в этом упражнении **на тот момент** (не с будущим максимумом) — работает одинаково для любого упражнения и веса, не требует ручной настройки порогов.
- `коэф_повторов` не даёт «зачекинить» уровень одним тяжёлым синглом — нужно 5+ повторов для полного коэффициента.
- Комбинация не позволяет фармить уровень ни чистым объёмом лёгких подходов (низкий коэф_веса), ни редкими тяжёлыми синглами (низкий коэф_повторов) — нужны одновременно вес и повторы.
- `best_weight_ever` обновляется инкрементально при каждом новом подходе (если текущий вес больше сохранённого).

**Уровни:** растут по накопленному XP/количеству подходов с порогами по нарастающей — стоимость каждого следующего уровня растёт в **×1.25** раза от предыдущего (более щадящая кривая, чем изначально предложенная ×1.4, — по фидбеку пользователя о том, чтобы прокачка не ощущалась muторной). Старт: уровень 1→2 = 100 (для шкалы «Сила», по XP) / N (для шкалы «Объём», по числу подходов — конкретное стартовое число задаётся как константа при реализации и легко донастраивается по ощущениям после запуска).

**Отображение прогресса:** на экране прогресс-бар каждой шкалы визуально показывает остаток до следующего уровня (от 0 до стоимости уровня), а не абстрактную кумулятивную сумму — реализуется как `текущий_totalXP - порог_текущего_уровня` из того же накопительного счётчика, без физического обнуления данных в БД.

**Анимация повышения уровня** — через библиотеку Motion, эффектный визуальный отклик при левелапе (см. раздел 3).

## 6. Каталог упражнений

337 упражнений, структурированы иерархически: **группа мышц** (Грудь, Спина, Ноги, Плечи, Руки, Корпус, Фулбоди, Кардио) → **подгруппа** (например для ног: Квадрицепс, Внутр, Биц бедра, Ягодицы, Внешн, Икры) → **название + оборудование** (штанга/гантели/блок/тренажёр/свой вес и т.п.). У каждого упражнения есть и русское, и точное (проверенное через веб-поиск по устоявшейся англоязычной фитнес-терминологии, а не машинным переводом) английское название.

Исходник каталога: `data/exercises.json` (337 записей, поля `id, slug, name_ru, name_en, muscle_group, sub_group, equipment`) — используется как seed-данные для таблицы `exercises` при разворачивании БД.

## 7. Экраны и UX-флоу

**Навигация:** нижняя таб-бар на мобильном (Тренировка / Прогресс / История), на широких экранах — то же самое боковым меню (адаптивная вёрстка с самого начала, мобильный use case в приоритете).

**1. Главный экран / Тренировка**
- Нет активной тренировки → крупная кнопка «Начать тренировку», под ней — последние 3-4 тренировки списком (не пустая заглушка).
- Есть незавершённая тренировка → баннер «Продолжить тренировку» сверху.
- Внутри активной тренировки: карточки добавленных упражнений с их подходами (вес/повторы + чекбокс «выполнено», по которому автоматически стартует таймер отдыха), кнопка «+ Добавить упражнение», кнопка «Завершить тренировку».
- Ввод подхода: вес + повторы через степпер (±2.5 кг / ±1 повтор) с возможностью тапнуть по числу для точного ручного ввода, автоподстановка значений из последнего подхода этого упражнения.

**2. Пикер упражнения** (по «+ Добавить упражнение»)
- Сверху — «Недавние»: 8-10 последних использованных упражнений, добавляются в один тап.
- Строка поиска.
- Ниже — дерево: группа мышц → подгруппа → список с оборудованием.

**3. Прогресс / Мастерство**
- Список упражнений с историей, у каждого — два индикатора уровня («Объём», «Сила») с прогресс-баром.
- Тап по упражнению → детальный экран: график веса по подходам во времени + прогресс XP.

**4. История тренировок**
- Переключатель **«Список / Календарь»**.
- Список: дата, длительность, кол-во упражнений/подходов, тап → просмотр тренировки целиком.
- Календарь: дни с тренировкой подсвечены (зелёным), тап по дню → список упражнений/подходов за этот день (если тренировок несколько — показываются все).

**5. Настройки**
- Переключатель языка интерфейса RU/EN (влияет и на тексты интерфейса, и на отображаемые названия упражнений — `name_ru`/`name_en` уже готовы в каталоге).
- **Экспорт данных** — сохранить резервную копию в файл.
- **Импорт данных** — восстановить из файла (полная замена текущих данных, с подтверждением).

**Онбординг:** без регистрации и welcome-туров — сразу рабочий главный экран. Пустое состояние = крупный CTA («Начать тренировку», подсказка «первый подход займёт 10 секунд»), а не текст «данных нет». Разрешения (уведомления, установка PWA) запрашиваются только в моменте, когда реально нужны, не при первом визите.

## 8. Резервное копирование и перенос данных (экспорт/импорт)

Вместо серверной синхронизации — файловый экспорт/импорт, как у GymKeeper и FitNotes.

1. **Экспорт** — по кнопке в настройках сериализуются все таблицы (`workouts`, `sets`, `exercise_progress`; каталог `exercises` не экспортируется — он статичен и уже есть в самом приложении) в один JSON-файл. На мобильном — через Web Share API (сохранить в облако/мессенджер по выбору пользователя), на десктопе — обычное скачивание файла.
2. **Импорт** — выбор ранее экспортированного файла → **полная замена** текущих локальных данных (с явным подтверждающим диалогом «это заменит текущие данные, продолжить?»). Сценарии использования: восстановление после переустановки/потери устройства, перенос на новый телефон.
3. **Напоминание о бэкапе** — ненавязчивое уведомление внутри приложения (например раз в 1-2 недели или после N-й тренировки), если давно не делали экспорт — снижает риск полной потери данных, если пользователь забудет сделать это сам.

Данные никогда не покидают устройство пользователя, кроме как явным действием «Экспорт» по его собственной инициативе.

## 9. PWA-специфика

- **Инструмент:** `vite-plugin-pwa` (обёртка над Workbox) — генерирует manifest и service worker по конфигу, без ручного низкоуровневого SW-кода.
- **Manifest:** `display: standalone`, тёмная `theme_color`/`background_color` под палитру приложения (раздел 10).
- **Кэширование:** весь app shell кэшируется при первой загрузке — приложение открывается и работает полностью офлайн, включая сам интерфейс.
- **Установка на главный экран:** без системного промпта при первом визите — событие `beforeinstallprompt` перехватывается и своя кнопка «Установить» показывается позже (например после первой завершённой тренировки или из настроек).
- **Обновления:** новая версия не подменяет текущую молча — показывается ненавязчивое «Доступно обновление», применяется по действию пользователя (чтобы не сбросить состояние посреди записи тренировки).
- **Будущая упаковка в APK:** упомянута пользователем как план на будущее. Стандартный путь — обернуть уже готовое PWA в Trusted Web Activity через **PWABuilder**/**Bubblewrap** (официальный Google-инструмент, бесплатно, без переписывания кода — тот же веб-код запускается как отдельное Android-приложение). Технически это шаг упаковки/дистрибуции ПОСЛЕ того как веб-версия готова и обкатана, не требует изменений в архитектуре, поэтому не детализируется в MVP-плане — вернёмся к этому отдельно, когда веб-версия будет готова.

## 10. Визуальный дизайн

- Тёмная тема по умолчанию + один акцентный цвет (без мультиколорной палитры).
- Крупная жирная типографика для ключевых цифр (вес, повторы, уровень).
- Карточки с лёгким glow/depth-эффектом вместо плоских bootstrap-теней.
- Графики прогресса с цветовой семантикой (цель/факт), не сухие таблицы.
- Главный экран — не более 3-4 ключевых метрик одновременно.
- Ориентиры: **Strong** (механика логирования), **Hevy** (полировка/анимации), **Copilot Money** (графики). Подробности и источники — [research.md](../../../research.md), раздел «Дизайн».

## 11. Тестирование и обработка ошибок

**Юнит-тесты (Vitest):**
- Формула мастерства (XP за подход, пороги уровней) — граничные случаи: 0 повторов, вес выше личного рекорда, первый подход по упражнению.
- Экспорт/импорт — round-trip тест (экспортировали → импортировали → данные идентичны исходным).
- Data layer функции — через `fake-indexeddb` (эмулирует IndexedDB в Node, совместим с Dexie).

**Осознанно не тестируем в MVP:** UI-компоненты автотестами, e2e-сценарии в браузере — ручная проверка на этом этапе достаточна.

**Обработка ошибок:**
- Валидация ввода — минимальная, на границе UI (вес/повторы — положительные числа).
- IndexedDB недоступен (приватный режим браузера, переполненное хранилище) — единственный по-настоящему критичный сценарий (без него приложение не работает вообще, данным больше негде жить); проверяется при старте приложения, показывается понятное сообщение вместо тихого сбоя.
- Импорт повреждённого/несовместимого файла — валидация структуры перед заменой данных, понятная ошибка вместо падения приложения.

## 12. Технологический стек (итог)

- **Фронтенд:** React + Vite, TypeScript, Tailwind CSS, Motion (анимации).
- **PWA:** vite-plugin-pwa.
- **Локальное хранилище:** Dexie.js (IndexedDB) — единственное хранилище данных, бэкенда и сервера нет.
- **Резервное копирование:** экспорт/импорт JSON-файла (Web Share API на мобильном).
- **Хостинг:** опционально, только статика (Vercel или любой другой) — не хранит и не обрабатывает персональные данные пользователей; для личного использования первое время можно вообще не деплоить публично.
- **Тесты:** Vitest + fake-indexeddb.
- **Будущая дистрибуция:** упаковка в APK через PWABuilder/Bubblewrap (TWA) — после того как веб-версия обкатана лично пользователем.
